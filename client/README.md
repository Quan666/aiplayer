# 映库客户端

Flutter + media_kit/mpv + SQLite。运行、四端构建、来源配置、同步和当前验收边界见 [根目录说明](../README.md)。

```bash
flutter pub get
flutter analyze
flutter test
flutter run
```

保留 pubspec.lock 使用已验证的依赖组合。SMB 插件位于 `../packages/aiplayer_smb`，不能只复制 client 而遗漏该目录。

## 海报图片链路

海报模糊曾有三处来源：显示解码统一限制长边 640 像素且未计算裁剪区域；同步缩图使用最近邻插值并连续降低尺寸和质量；同步小图与在线图片共用路径，命中后长期不升级。

| 阶段 | 当前规则 |
| --- | --- |
| 来源 | TMDB 小尺寸提升至 w780，保留更大尺寸和 original；Bangumi 使用大图。未知来源保留完整 URL。 |
| 磁盘 | 在线下载保留响应原始字节至 `.source.image`；旧 `.image` 和同步图片作为离线回退。可见时按需升级，原图完成前保留旧画面，同步不降质覆盖原图。 |
| 显示 | 按布局、设备像素比例和 cover 裁剪计算解码尺寸，64 像素分档；普通图片长边上限 1280，全屏查看器上限 4096。不将低分辨率源图放大解码。 |
| 同步 | 合规小图保留原字节；超预算图片校正方向，从原始像素做面积平均缩放，优先调整 JPEG 质量，再降尺寸。保留 4:4:4，压缩后仍满足原有 134970 字节预算。 |
| 执行 | 文件读写及显示解码使用异步平台实现；压缩在同步 worker 或 compute isolate 执行。下载最多 4 个、海报墙解码最多 2 个；升级复用下载队列、退避和生命周期控制，无轮询定时器。 |

清理图片缓存会同时清理两层文件。旧版本缓存没有来源标记，因此首次可见时可能重新下载一次清晰图；离线时继续显示已有图片。源图本身过小、极端裁剪达到解码上限时，仍无法恢复缺失的细节。

验证包括高 DPR 的实际解码像素、细线缩放、同步体积预算、缓存修订与并发恢复、升级保留旧图、离屏取消，以及 paused 后不再产生新帧的暂停与恢复。完整海报墙 profile 场景使用 640 张图片、独立连接后台写入、往返滚动和 9 次切页。Linux / Xvfb 软件渲染仅用于回归，不能代表 Android 真机帧率或功耗；本轮没有真机画质、内存峰值及耗电数据，也没有同环境改动前后的性能对照。

2026-11-01 的最终 profile 记录：640 张全部解码，9 次切页，202 次后台提交及通知，已有源图的网络请求为 0。连续滚动并后台写入的 build/raster P95 为 3.138/12.945 ms，全库冷遍历为 23.170/16.591 ms，切页为 16.383/30.449 ms；软件渲染下仍存在超帧预算，不能据此宣称所有场景流畅。完整报告生成于 `.local-build/reports/poster-clarity-final/library-artwork-performance.json`。
